# 本地小模型运筹优化 Agent 推进计划

日期：2026-10-04。状态：运输增量与不可行诊断已实现，其余路线仍在规划，真实小模型效果待测。

实施进展（同日）：已完成首个运输增量，包括能力边界清单、运输输入合同、受限中文解析、真实求解与独立验算、多项原子编辑、本机模型待确认草稿接口，以及 40 条开发解析案例和 8 条待运行的真实模型案例。使用方法见 [运输分配增量说明](../examples/transportation_sample.md)。本机常用 Ollama 端口未发现服务，因此未记录真实小模型成绩；下文其余模板、通用语义合同和冻结评测仍属规划。

后续增量已补充运输不可行诊断：求解器返回 `INFEASIBLE` 时，系统基于原始供需和线路合同报告总供给短缺、需求点可达供给不足、无有效需求线路的供给点，或提示需要进一步检查网络割集。诊断是证据摘要，不冒充完整 IIS；修改供需、线路或禁运条件后再重新求解。

2026-10-07 规则解析基线运行 40/40 通过，覆盖七类模板的路由、需求门控和带参考目标的求解验算；报告明确标记为本地规则基线，不计作真实小模型成绩。下一项可执行工作是接入本机兼容模型并运行 8 条运输抽取案例；当前尚无可记录的本机模型服务结果。

本轮目标是让本地部署的小规模语言模型，在明确支持的运筹优化任务上，可靠完成需求理解、澄清、建模调度、求解和解释。近期优先扩充可执行模板、提高解析准确性，并建立本地模型评测；SFT 和 GRPO 根据评测结果后置。

本文调整 [双主线路线](two-track-roadmap.md) 中以云端开源模型后训练为主的近期顺序。Agent System 与语言模型仍分开评测；已有恢复策略保留。训练地点与推理地点解耦，最终推理以本地为目标。

## 2. 面向小模型的职责划分

目标是减少一次语言模型调用需要完成的独立决策。模型负责理解表达和选择受限动作；程序负责校验、状态变更、编译和数学计算。

```mermaid
flowchart LR
    U[用户描述与数据] --> R[规则与模板候选召回]
    R --> L[小模型提取结构化需求]
    L --> C[来源、单位、约束覆盖检查]
    C -->|信息缺失或含义不明| Q[针对性澄清]
    Q --> U
    C -->|信息完整且能力支持| M[模板编译与执行计划]
    M --> S[求解器]
    S --> V[独立验算]
    V --> E[结果解释或有界修复]
```

复用现有工作流节点，避免把每个职责都变成一次 LLM 调用。首版常规完整输入争取一次结构化解析；候选歧义时再拆分识别与抽取，并分别测量正确率和延迟。

第一阶段采用两层结构：业务模板参数与受限约束，编译到可执行模型。线性部分优先评估复用已有 `LinearModel`；保留业务模板标识和约束来源。暂不统一重写已有六类求解器，也不让小模型直接生成任意 Python/Gurobi 代码。

## 3. 模板扩展次序

| 优先级 | 模板 | 首版范围 | 暂不纳入的范围 |
| --- | --- | --- | --- |
| P0 | 现有六类业务模板与显式 LP/MILP | 建立真实能力清单，补齐解析与拒绝边界 | 不把说明文本当作已执行约束 |
| P1-1 | 运输分配 `transportation` | 单周期、单商品、供给上限、需求满足、线性运输成本、显式禁运线路 | 多商品、转运、车辆路径 |
| P1-2 | 集合覆盖 `set_cover` | 选择集合的成本最小化，每个需求点至少覆盖一次 | 自动推断空间覆盖半径、多目标公平性 |
| P1-3 | 配料 `blending` | 固定总量、成分上下界、原料供给与线性成本 | 非线性混合性质、未定义的百分比分母 |
| P2 | 员工排班 `workforce_scheduling` | 班次需求、可用性、资格和工作量上限 | 未确认的法规规则、复杂轮休与偏好体系 |
| P2 | 多期库存生产 `inventory_planning` | 库存平衡、产能、持有成本、显式初始库存 | 未声明的缺货、随机需求与服务水平 |
| P3 | 最小费用流、CVRP、VRPTW | 按需求逐个建立独立数据合同和验证器 | 首轮不承诺复杂路径问题的统一支持 |

选择前三类，是因为它们能分别补充供需平衡、覆盖选择和比例约束，便于复用 LP/MILP 基础设施并建立人工可检查的小实例。这是工程优先级判断，尚未通过业务频率数据验证。

运输模板中供给可有剩余，但不能默认允许需求缺口；不得静默添加虚拟供给或缺货罚金。配料比例必须先确认总量与单位，才能转成线性约束。

每个模板完成以下交付才算支持：

1. 版本化输入 Schema、必填字段、单位、允许的目标方向与约束类型。
2. 中文别名、易混淆反例、缺失字段的澄清问题。
3. 参数与实体引用校验、确定性编译或求解适配器。
4. 业务层独立验算，包括约束和目标值复算。
5. 小实例参考答案、正常和异常样本、可运行端到端示例。
6. 注册到需求解析、数据合同、MCP 能力发现及结果展示链路。

模板必须区分“可识别”“可抽取”“可求解”“可验算”，只有完整链路通过验收才对外标记为可求解。业务名称可以作为同一模板的别名，不能靠增加名称虚增覆盖量。

## 4. 需求解析与约束覆盖

### 4.1 先确定语义合同

扩展现有 `RequirementBrief` 与 `dialogue_contract`，不另建一份会漂移的会话状态。首版字段应至少包含：

| 信息 | 必须保存的内容 |
| --- | --- |
| 意图 | 分析、求解、补充、修改、撤销、比较或暂停 |
| 问题类别 | 候选模板、选择依据、待澄清差异；允许未知类型 |
| 目标 | 最大化/最小化、指标、单位；多目标的优先级不明时追问 |
| 实体与参数 | 实体标识、集合、数值、单位、表格列或消息中的来源 |
| 约束 | 稳定标识、受支持类型、对象、比较符、阈值、硬约束/偏好 |
| 来源与状态 | 来源轮次、原文片段或数据单元引用；已编译、需澄清、不支持 |
| 变更 | add/replace/remove、目标字段或约束标识、原值、新值、父版本 |

类型正确只代表结构符合合同。还要检查实体存在、单位兼容、目标方向、上下界、字段完整性，以及每条业务要求是否被处理。未指定的硬约束和偏好罚分不能自行补齐。

### 4.2 分阶段解析

1. **候选召回**：使用关键词、数据列特征与已有会话状态返回少量候选。相似度不能当作经过校准的正确概率；候选数和拒绝阈值在验证集确定。
2. **受限抽取**：只向小模型提供候选模板的相关 Schema、少量示例、当前有效状态和必要数据摘要。完整数值表由程序管理，用引用绑定到模型。
3. **语义校验**：识别“至少/至多/恰好”、否定、每个与总计、金额和时间单位、冲突与缺失。保留未能解释的子句，不允许直接丢弃。
4. **澄清或编译**：有未解决的硬约束、未知操作、缺失数据时暂停求解；信息完整后执行确定性变更并生成模型。
5. **需求回显**：展示实际将执行的目标、关键约束、假设和数据版本，用户可更正；完整且无歧义的输入可以直接执行，无需每轮固定确认。

原文片段由模型引用后，程序可以检查引用确实存在，但这仍不能证明它与约束含义一致。评测需要人工语义标注和反例；运行时的来源、覆盖和规则检查用于降低遗漏风险，不宣称已实现任意自然语言的等价性证明。

### 4.3 贯穿验收示例

用户说：“从这些项目中选择，总预算不超过 20 万元，至少选 3 个，A 和 B 不能同时选，收益尽量高。”

期望识别为带扩展约束的 0-1 选择：收益最大化、预算上限、选择数量下限、互斥关系。若数据中的成本单位是元，应将预算规范为 200000 元并记录换算来源；成本单位未知时先澄清。

当前基础背包不能因为识别出“预算”就忽略数量和互斥。实现对应扩展后，编译为预算约束、选择数量约束与 A/B 互斥约束，并逐条验算；扩展完成前明确说明尚不能完整执行。

第二轮“预算改成 15 万，取消至少选 3 个，其他不变”，应原子修改预算并删除对应约束，保留互斥。任一变更含义不明时保持旧有效版本，澄清后整体提交，避免一半新状态、一半旧状态。

## 5. 执行规划如何服务小模型

首版 Planner 采用可审计的有限动作：澄清、读取数据、校验、编译、求解、验算、解释或终止。每步记录前置条件、输入版本、输出与失败出口；不要要求小模型生成长篇自由计划再尝试执行。

信息完整且在模板能力范围内，才开放编译和求解动作。缺列进入补数据；未知单位进入澄清；结构错误最多进行一次受控重试；已证明不可行进入诊断与用户需求修订，不重复调用同一个模型期待变可行。求解超时与不可行必须分别处理。

已有 Recovery Policy 继续服务其已验证的任务范围。新模板和解析动作先用规则策略，不能直接假定旧 checkpoint 对新动作空间有效。

## 6. 本地模型接入与评测配置

先复用 `LLMConfig` 的 `base_url` 和模型配置。增加服务能力探测、结构化输出适配、连接/生成超时、输出长度限制、可取消请求和运行记录。首轮不绑定模型品牌，具体模型、量化和上下文长度待目标设备确定。

Ollama 官方文档提供 JSON Schema 约束输出，并说明兼容接口可通过 `response_format` 使用；vLLM 也提供结构化输出能力。具体接入参数须按部署版本验证，不能因兼容聊天接口就假定全部参数都兼容。来源：[Ollama 结构化输出](https://docs.ollama.com/capabilities/structured-outputs)、[vLLM 结构化输出](https://docs.vllm.ai/en/latest/features/structured_outputs/)（查阅日期：2026-10-04）。

结构化解码可以约束输出格式；内容含义仍由语义检查和评测负责。服务不支持所需约束时，明确记录降级模式，校验失败最多修复一次，随后澄清或报告失败。正式本地评测禁用远程兜底，并记录模型是否实际参与，防止规则成功被误记成模型成功。

比较设备可承载的两个模型规模；同一权重的不同量化版本单独记录。记录硬件、内存/显存峰值、模型与量化版本、提示词版本、上下文长度、采样配置、首轮成功率、一次修复后的成功率，以及解析和端到端延迟的 P50/P95。冷启动与热启动分开测量。

本地完整运行还包括 RAG、MCP 和求解器。当前 Gurobi 许可仍是部署条件；模型离线运行不等于求解环境无依赖。首轮沿用现有可用求解环境，把可替换的开源求解后端作为单独任务评估。

## 7. 评测集与验收标准

第一轮建设约 200 条单轮输入与 50 段多轮会话，按可用人力分批交付。覆盖现有模板、前三个新增模板、显式数学模型、信息不足、类型混淆、单位、否定、额外约束、无关问题和不支持任务。

先按基础实例、业务结构和生成来源分组，再划分训练/开发/验证/冻结测试。同一实例的改写、数值变体与整段会话必须在同一组，测试问题及其改写不能进入检索示例库。人工独立撰写一部分测试问题；模板生成数据单独报告，避免循环验证。

每条样本保存期望动作、规范化需求、原文约束与模型约束的对应关系、允许的澄清问题，以及适用时的可行性或参考目标值。多解问题比较约束满足与目标值，不强制匹配唯一决策向量。

| 指标 | 建议首轮目标 | 计算口径 |
| --- | --- | --- |
| 已支持任务路由准确率 | ≥95% | 与未知类型拒绝率、覆盖率分开报告 |
| 关键参数与约束准确率 | ≥95% | 分项报告实体、比较符、数值、单位及约束 precision/recall |
| 未支持/缺失信息的正确处理 | ≥95% | 正确澄清或拒绝，且未提前调用 Solver |
| 已接受请求的静默约束遗漏 | 冻结测试中观察为 0 | 同时报样本数；零观察不代表真实概率为零 |
| 完整支持任务端到端成功率 | ≥90% | 需求语义正确、构建成功、求解状态恰当且验算通过 |
| 多轮需求变更正确率 | ≥95% | 所有指定操作完成，其他已确认信息保留 |
| 本地资源与延迟 | 待硬件基线后设定 | 固定任务规模、上下文、量化与并发条件 |

这些是建议门槛，不是现有成绩。指标报告给出分母、按模板和难度分层的结果；信息不足任务的正确澄清、不可行任务的正确诊断，另计任务处理成功，不能混入“得到可行解”的成功率。为防止系统靠一直追问提高准确率，同时报告完整输入的直接完成率、澄清轮数及重复问题率。

至少做四组对照：现有规则；同一小模型直接生成结构化需求；小模型加模板 Schema；小模型加 Schema、语义校验与澄清。各组使用相同求解器、预算和数据；记录被规则兜底的比例。之后才增加微调版本，验证系统设计与模型训练各自带来的收益。

求解验算通过只证明结果满足已建立模型。训练样本还必须通过语义标注检查，不能只依据 Solver/Verifier 成功就自动进入高质量 SFT 数据集。

## 8. 实施顺序与代码落点

| 阶段 | 交付内容 | 主要落点 | 退出条件 |
| --- | --- | --- | --- |
| M0：基线与合同 | 能力清单、首批人工标注样本、指标定义、目标设备基线 | `templates/registry.py`、现有 tests、拟新增解析评测数据与脚本 | 能复现现有错误并区分路由、抽取、编译和求解问题 |
| M1：注册与首个模板 | 统一能力元数据，运输分配完整求解与验算链 | `templates/registry.py`、`solver_registry.py`、`mcp_validation.py`、`solution_verifier.py`、MCP 服务 | 从标准数据到结果可复现，现有模板无回归 |
| M2：本地解析闭环 | 结构化抽取、单位/来源/覆盖检查、澄清、本地模型适配 | `requirement_analysis.py`、`llm.py`、`dialogue_contract.py`、`schema_mapping.py` | 现有模板与运输模板的自然语言端到端评测可运行 |
| M3：扩展与多轮 | 集合覆盖、配料；类型化约束和多项原子变更 | 模板编译模块、`linear_model.py`、`dialogue_contract.py` | 每项扩展具备独立验算和异常测试 |
| M4：执行规划与评测 | 受限动作、预算、错误分类、对照实验报告 | `api/services/agent_workflow.py`、评测脚本与运行记录 | 达到预设门槛或有明确错误分布及改进决策 |
| M5：针对性 SFT | 按错误类别采集和校正数据，训练并与基线比较 | 后续新增模型训练目录 | 独立测试证明理解或动作质量提升，再决定是否 GRPO |

M1 与 M2 按一个模板的小闭环交替推进，避免先扩出大量只有描述没有可靠解析的模板。统一注册表只归集元数据和接口引用，求解逻辑仍按模块分离；已有 `ProblemSpec` 保持展示/兼容职责，类型化需求通过适配层逐步接入。

首个可交付增量建议包含：

1. 现有七个入口的能力清单与至少 40 条人工标注回归案例。
2. 运输分配的 Schema、求解、独立验算、正常与异常示例。
3. 一条本地小模型的自然语言到运输参数的受限抽取链。
4. 针对缺失需求、禁运线路、单位不明和额外限制的澄清流程。
5. 一份规则/小模型对照报告，含失败样例和设备资源记录。

最终验收场景：用户用自然语言描述运输业务并提供数据，系统识别运输分配而非仓库选址，保存目标与全部约束，必要时澄清，求解并独立验算；用户修改供给后只更新指定参数重新计算。全过程通过本地模型服务完成，无远程模型兜底。

## 9. 后续决策依据

若主要错误来自遗漏条件和多轮编辑，优先完善语义合同与训练样本；若输出格式错误多，先改结构化解码；若题型已正确但编译失败，修复模板编译器；若解析正确但求解耗时高，处理求解配置与模型规模。不要把所有失败都归因于模型参数量。

SFT 首先训练模板判别、参数抽取、约束识别和修订操作。GRPO 只有在语义正确性奖励、冻结评测集和训练预算明确后再安排，避免模型通过省略难约束获得更高求解奖励。

尚待确定：目标设备及内存/显存、优先服务的真实业务场景、可用于标注的数据与可接受的交互延迟。未确定前，模板和合同设计可以继续；不预先承诺具体模型与性能。
